## Summary

The Draoi layer was added on 2026-11-20, but the CLI and workflow docs still assume two library roots (`Dia/`, `Cluiche/`). An audit on 2026-11-23 found the following:

- The "Dia never depends on Draoi" rule is not checked. Only the build guards it, because no Dia `.vcxproj` puts `Draoi/` on its include path.
- `dia check deps`, `dia check arch`, `cppcheck`, `clones` and `spec-sync` skip `Draoi/` or give wrong results for it.
- `dia docs test-scaffold` breaks on Draoi headers, and `dia scaffold module` can't target Draoi.
- The module schema has no Draoi layer value. Draoi docs borrow `foundation/application` and hang off `dia.root`.
- The skills and steering docs describe two layers.

This plan fixes all of the above. It also fixes two gaps found along the way: `dia check deps` skips every top-level module, and `module-registry.md` prints the module tree 4 times.

## Decisions (made for this plan; change them here before Task 2 if you disagree)

- **D1 — Layer value.** Add one layer value, `draoi`, and keep a single tier. A sub-tier split such as `draoi/core` vs world packages is not needed yet. Draoi-to-Draoi ordering is covered by declared dependencies and `forbidden` lists.
- **D2 — Root doc.** Add `Draoi/dia.draoi.root.architecture.module.md` with `module_id: draoi.root`, mirroring `dia.root`. Draoi package docs use `parent_module_id: draoi.root`. Doc filenames keep the `dia.*.architecture.module.md` pattern, because every tool globs on it.
- **D3 — Boundary rule keyed on the root folder.** "Code under `Dia/` must not include a module under `Draoi/`" is a separate check in `dia check arch`. It does not use layer ordering, so it also catches Dia modules whose layer does not parse (for example `tools/editor` and `4.1-*`, which `parse_layer` skips today). `parse_layer("draoi")` returns major 5, above every Dia layer, as a second guard.
- **D4 — One source of truth for library roots.** Add a new `dia_cli/utils/library_roots.py` with `LIBRARY_ROOTS = ("Dia", "Draoi")`, plus helpers to iterate module docs and strip the root from a module path. Every command in this plan uses it instead of hardcoding `"Dia"`.
- **D5 — deps reads both dependency keys.** Declared dependencies are the union of `dependent_modules` and `dependencies.required`. There's no doc migration.
- **D6 — sln folder.** The `draoi` layer maps to the existing top-level `Draoi` solution folder (GUID `{3F9A7C21-...}`), not nested under `Dia`.

## Open Design Questions

- After Task 4 widens `deps`, about 120 top-level Dia modules are checked for the first time. If Task 5 finds hundreds of findings, do we fix them all now or baseline them, the way `cppcheck --accept-baseline` does?
- Should `dia check arch` also enforce Application → Draoi direction rules, for example forbidding Draoi from including `Cluiche/*`? Right now nothing scans the application folders as modules. A Draoi → Application include would fail to build, because Draoi projects don't have app include paths. That is the same build-only protection Dia ↛ Draoi has today.
