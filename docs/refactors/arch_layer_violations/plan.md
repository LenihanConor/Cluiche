# Refactor Plan — Architecture Layer Violation Remediation

**Spec:** none (tech-debt remediation across existing modules, not new feature work)
**Scope:** 6 independent violation clusters surfaced by `dia check arch` (the user-supplied error list was a curated excerpt, not the full output — the full run reports 172 violations at baseline; the 6 clusters below cover the ones with a paste-supplied excerpt, other unrelated pre-existing violations exist outside this plan's scope, see task 3's note on `DiaEntitySpatial`/`DiaSchemaBrowser`).

## Session Notes — Audit Summary

`dia check arch`'s full output (172 violations at baseline, confirmed via `git stash`/re-run) spans many more root causes than the 6 clusters in the original curated error list this plan was scoped to. One cluster (VisualDebugger family → `DiaVisualDebugger`) was already a documented loose end in `docs/BACKLOG.md` ("DiaVisualDebugger layer tag conflict") calling for "a proper audit" before deciding a fix — this plan is that audit, plus audits of the other 5 clusters found in the same excerpt. Tasks 1–6 are landed; current count is 115 (net -57, no regressions, confirmed via baseline re-run). Two clusters (B, F) turned out to be simple mistags rather than real boundary problems — worth checking "is the layer tag just wrong" before reaching for interface extraction, since it's cheaper when it applies.

Violations are derived purely from real `#include` paths matched against each module's `path:` in its `dia.*.architecture.module.md` frontmatter, compared via `layer:` tags (`Dia/DiaCLI/dia_cli/commands/check/arch_checker.py` + `arch_module_map.py` + `arch_include_parser.py` + `arch_layer_rules.py`). The `dependent_modules` list is decorative and never consulted, and **there is no allowlist/exception mechanism** — a "sanctioned" cross-dependency (e.g. binding decision SD-002) must be resolved by making the physical layer tags/module boundaries agree, not by declaring an exception.

**Cluster D — RigidBody2DVisualDebugger → `DiaGraphics/Misc/RGBA.h` (trivial):** the codebase already has a foundation-tier `DiaCore/Colour/RGBA.h` used elsewhere (`DebugGroupAccents.h`, `IDebugDomain.h`) instead of the domain-tagged `DiaGraphics/Misc/RGBA.h` — looks like a leftover duplicate type. Fix: repoint the one include, after confirming field-compatibility.

**Cluster C — GridVisibilityVisualDebugger → DiaGridVisibility + DiaPathfinding (trivial):** every other `Dia<X>VisualDebugger` is tagged `domain/<X's own domain>/tools` (e.g. Animation2D → `domain/animation/tools`, SoftBody2D → `domain/physics/tools`). `DiaGridVisibilityVisualDebugger` is the outlier, mistagged `domain/visual/tools` instead of `domain/gameplay/tools` (matching `DiaGridVisibility`/`DiaPathfinding`, both `domain/gameplay/core`). Its module.md's own attempted self-documented exception is also broken (malformed `dia.dia*`-prefixed ids, an inline comment baked into a forbidden-list value) — a no-op today regardless. Fix: retag + fix the malformed ids.

**Cluster E — `dia.root` false attribution, DiaSensor + DiaTriggerScript (metadata-only):** both modules have their own module.md, but neither declares a `path:` key, so the checker never recognizes their directories as their own module and sweeps their files into `dia.root` (`foundation/core`, the most restrictive layer). `DiaTriggerScript` also has a duplicate `module:`/`id:` key collision that mangles its module id, and both use non-standard `layer:` strings and dependency-list shapes the parser doesn't recognize. Once corrected, their real dependencies are all downward from a `domain/gameplay/core`-tier module — this is a pure doc-metadata bug, not a real layering violation.

**Cluster F — DiaSimTime → DiaSaveGame (done — turned out to be a mistag, not a boundary problem):** Original hypothesis was that `dia.savegame` (`domain/gameplay/core`) needed an `IDebugContext`-style interface extraction, since `dia.simtime` (`foundation/application`) only needs `ISaveable`/`SaveContext`/`LoadContext`. Built that extraction (moved the 3 headers + added an `ISaveRegistry` interface for the `SaveRegistry*` DiaSimTimeModule also holds) — but a simpler question surfaced first: is `dia.savegame` even correctly tagged `domain/gameplay/core`? Its own module.md already documented "no domain imports" and forbade `dia.entity`/`dia.economy`/`dia.applicationflow`/`dia.blackboard` as dependencies; its only real deps (`dia.core`, `dia.serializer`) are both foundation-tier; and only `DiaSimTimeModule` + tests depend on it externally (no game/app code yet). Same mistag shape as cluster B's `DiaEditor`. **Retagging `dia.savegame` to `foundation/services` alone fixed all 4 sub-violations**, so the extraction work was reverted (moved the 5 files back, deleted `ISaveRegistry.h`, restored all includes/vcxproj entries) to keep the diff minimal — confirmed via `git status`/`git diff` that the working tree matches HEAD except for the two `layer:`/schema doc edits. Verified: 119 → 115 violations, no new ones.

**Cluster A — VisualDebugger family → `dia.debug.visualdebugger` (largest, the pre-existing Loose Ends item):** hits Animation2D/IK2D/Rig2D/SoftBody2D/AssetRuntime visual debuggers (per the existing BACKLOG note, ~42 files total across every domain visual debugger). Three headers involved: `Domain/IDebugDomain.h` and `Domain/DebugGroupAccents.h/.cpp` are graphics-free (only StringCRC/RGBA/json + a forward decl); `DebugLayerManager.h/.cpp` is not — it stores/returns `Camera2D`/`ViewportTransform`/`Camera3D` by value and touches `DebugFrameDataVisitor`, a real `DiaGraphics`/`DiaGraphics3D` dependency. `DiaDebugDraw` (the abandoned R6 split target from the `layer-formalisation` spec) already exists, tagged `foundation/services`, and already duplicate-compiles `DebugLayerManager` et al. via relative path out of `DiaVisualDebugger` — but its own module.md still lists `dia.graphics` as required, which is itself contradictory for a `foundation/services` tag (the exact tension the BACKLOG entry flagged as unresolved). `IDebugDomain`/`DebugGroupAccents` are not currently part of `DiaDebugDraw`'s compiled set at all. Fix: (1) move the two graphics-free headers into `DiaDebugDraw` now; (2) audit call sites and decompose `DebugLayerManager` into a graphics-free `DebugLayerRegistry` (moves to `DiaDebugDraw`) vs. camera/viewport glue (stays in `DiaVisualDebugger`), following the `IDebugContext` decoupling pattern for any camera/viewport data domain debuggers still need; (3) remove the duplicate-compile vcxproj hack; (4) reconcile the `layer-formalisation` R6 task + SD-002 wording once tags and code agree.

**Cluster B — DiaScalarFieldInspector → DiaEditor (done, retag landed; one follow-up spawned):** `DiaEditor` was tagged `domain/visual/core` but is actually a cross-cutting editor-plugin host framework, not visual-domain content. Confirmed its 5 required deps (`dia.json`, `dia.observation`, `dia.debugprotocol`, `dia.game`, `dia.protobuf`) are all foundation-tier, and its 13 known dependents are all `domain/*/tools` (downward deps, always allowed) — so retagging `dia.editor` to `foundation/application` was safe and landed (task 6). It fixed the `DiaScalarFieldInspector` violation, but re-running `dia check arch` surfaced a **new** violation the pre-check research missed (it only checked module.md-declared deps, not DiaEditor's own actual `#include`s): `Dia/DiaEditor/UI/WebUIBridge.cpp` includes `<DiaUI/IUISystem.h>` (`domain/visual/core`), an undeclared dependency that was fine when DiaEditor was itself `domain/visual/core` (same-domain/same-tier) but is now an upward violation. It's contained to one file — `WebUIBridge` only calls `RegisterJSHandler`/`CallJSFunction` on `IUISystem*`, both already separable JS-bridge concerns on that interface. User decision: keep the retag (net violation count unchanged — one violation swapped for another, but the original inter-domain mistag is fixed) and track the `DiaEditor`→`DiaUI` fix as its own task (11) rather than fix inline, since it needs its own small interface-extraction design (mirrors the `IDebugContext`/cluster F precedent: pull a narrow `IJSBridge` interface — just `RegisterJSHandler`/`CallJSFunction`/the `JSHandler` typedef — into a foundation-tier home, make `IUISystem` inherit it, repoint `WebUIBridge` to depend on the narrow interface instead of `IUISystem` directly).
