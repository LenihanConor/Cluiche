## Purpose

Provide the editor with knowledge of available module and PU types so that "Add Module" and "Add PU" dialogs can offer autocomplete and type selection. In static mode this comes from a generated `types.json` file; in live mode from the game's TypeRegistry via WebSocket query.

## Acceptance Criteria

1. **Type list** — Editor knows the set of available module type_ids (registered via DIA_MODULE macro, SD-008) and PU types.
2. **Static mode source** — Reads a `types.json` file generated by DiaCLI (`dia types export`). File lives alongside the `.diaapp` manifest or in a well-known location.
3. **Live mode source** — When connected to a running game, queries TypeRegistry via DiaAPI command for the current set of registered types.
4. **Autocomplete** — "Add Module" dialog offers autocomplete from the type list for the `type_id` field.
5. **Unknown type warning** — If a manifest references a `type_id` not in the known type list, show a warning (not error — type might exist but types.json is stale).
6. **Refresh** — User can manually refresh the type list (re-read types.json or re-query live game).

## Design

### types.json Format

Generated by `dia types export --output <path>`:

```json
{
    "generated": "2026-05-19T10:30:00Z",
    "modules": [
        { "type_id": "KernelModule", "description": "Window and input management" },
        { "type_id": "TimeServerModule", "description": "Frame time provider" },
        { "type_id": "RenderModule", "description": "Canvas renderer" }
    ],
    "processing_units": [
        { "type_id": "ProcessingUnit", "description": "Default PU type" }
    ]
}
```

### Type Registry (C++ Backend)

```cpp
namespace Dia::ApplicationFlow::Editor {
    struct TypeInfo {
        Dia::Core::StringCRC typeId;
        const char* description;
    };

    class TypeDiscoveryService {
    public:
        void LoadFromFile(const char* typesJsonPath);
        void LoadFromLiveGame();  // queries via WebSocket
        void Refresh();

        unsigned int GetModuleTypeCount() const;
        const TypeInfo* GetModuleTypes() const;
        unsigned int GetPUTypeCount() const;
        const TypeInfo* GetPUTypes() const;

        bool IsKnownModuleType(Dia::Core::StringCRC typeId) const;
        bool IsKnownPUType(Dia::Core::StringCRC typeId) const;
    };
}
```

### Frontend Integration

- `editor.types.getModuleTypes()` → returns array for autocomplete
- `editor.types.getPUTypes()` → returns array for PU add dialog
- `editor.types.refresh()` → triggers reload
- Event: `onTypesLoaded` → UI updates autocomplete lists

### Discovery Priority

1. If live-connected → use live TypeRegistry (always current)
2. Else → load `types.json` from same directory as open `.diaapp`
3. If neither available → type fields are free-text (no autocomplete), no unknown-type warnings

### Validation Integration

The Real-Time Validation feature can optionally flag `UNKNOWN_TYPE_ID` as a warning when a module's type_id isn't in the known list. This is advisory — not an error — because types.json may be outdated.

## AI Review Questions

| # | Section | Question | Answer |
|---|---------|----------|--------|
| 1 | Location | Where should types.json live? | Same directory as the `.diaapp` file, or a `Cluiche/out/<App>/` directory. Editor searches both. DiaCLI outputs to the out/ path by default. |
| 2 | Staleness | Should the editor warn if types.json is older than the last build? | No — just surface unknown-type warnings on individual modules. Global staleness warning adds noise. User can refresh manually. |
| 3 | Live | Should the editor auto-refresh types when live connection is established? | Yes — on connect, automatically query TypeRegistry and update the type list. No manual step needed. |
| 4 | Scope | Should types.json include stream payload types or just module/PU types? | Just module and PU types for now. Payload types are application-defined strings — no registry for them. Free-text in the stream editor. |
