# Feature Spec: registered-types-schema

**Parent:** @docs/specs/systems/dia/diacli.md
**Status:** Done
**Plan:** @docs/specs/features/dia/diacli/registered-types-schema.plan.md

## Summary

Generate `registeredtypes.diaschema` — a build-time JSON file that captures all C++ registered types (components, modules, processing units) from a fully-linked game binary. Editor tools read this file instead of the C++ singletons they can't link against, giving them a complete, game-scoped type catalogue without coupling to any game binary.

## Problem

C++ type registries (`ComponentRegistry`, `TypeRegistry`) are populated via static initialisers at link time. The editor process never links the game binary, so its dropdowns are always empty. This affects:
- **DiaBlueprintEditor** — "Add Component" dropdown shows nothing
- **DiaApplicationFlowEditor** — module/PU type dropdowns already read `types.json` (via `TypeDiscoveryService`) but that file has no generation spec and no versioning

## Goals

- Blueprint editor component dropdown populated with all registered components for the loaded game
- Application flow editor module/PU dropdowns populated from the same source
- Each game's schema is scoped to that game's binary — CluicheTest and a future CoW game have separate files
- Schema is versioned: editors can detect breaking changes and warn users
- `.diagame` manifest references the schema file for discovery

## Acceptance Criteria

### AC-1: Schema file generated by `dia reflect`

- `dia reflect --target <diagame>` runs the game binary with `--dump-schema`, captures stdout, writes `registeredtypes.diaschema` alongside the `.diagame`
- Generated file location: `Cluiche/Assets/<GameName>/registeredtypes.diaschema`
- Command exits non-zero if binary not found, dump fails, or output is malformed

### AC-2: Schema file format

```json
{
  "version": { "major": 1, "minor": 0 },
  "game": "cluichetest",
  "components": [
    {
      "type_id": "cluichetest.transform",
      "debug_name": "TransformComponent",
      "fields": [
        { "name": "x", "kind": "primitive" },
        { "name": "y", "kind": "primitive" }
      ]
    }
  ],
  "modules": [
    {
      "type_id": "EntityModule",
      "description": "Manages entity lifecycle",
      "allowed_pus": "sim"
    }
  ],
  "processing_units": [
    {
      "type_id": "MainProcessingUnit",
      "description": "Main thread PU"
    }
  ]
}
```

### AC-3: Versioning

- `version.minor` is auto-incremented by the generation script on every run where the type set changes (new type added, new field added)
- `version.major` is incremented when `--breaking` flag is passed, signalling a breaking change (type removed, field removed, type renamed)
- If no schema file exists yet, starts at `1.0`
- Script diffs previous file vs new output to determine if minor should increment; if nothing changed, version is unchanged and file is not written (no spurious git diffs)

### AC-4: `.diagame` references the schema

- `.diagame` manifest gains a `"schema"` key: `"schema": "registeredtypes.diaschema"`
- Path is relative to the `.diagame` file
- `dia validate manifest` validates that the referenced schema file exists if the key is present

### AC-5: Game binary supports `--dump-schema`

- CluicheTest (and any future game binary) accepts `--dump-schema` flag
- Writes JSON to stdout: `{ "components": [...], "modules": [...], "processing_units": [...] }`
- Components sourced from `Dia::Entity::ComponentRegistry`
- Modules and PUs sourced from `Dia::ApplicationFlow::TypeRegistry`
- Binary exits 0 on success

### AC-6: DiaBlueprintEditor reads schema on project load

- When `.diagame` loads, blueprint editor reads `registeredtypes.diaschema` from the diagame directory
- `BuildAvailableComponentsJson` uses schema data instead of `ComponentRegistry::Get()`
- If schema file absent: dropdown shows empty list with status message "No schema found — run `dia reflect`"
- If schema `version.major` has changed since last load: status bar warning "Schema major version changed — blueprint files may reference stale types"

### AC-7: DiaApplicationFlowEditor uses schema (migration from `types.json`)

- `TypeDiscoveryService::LoadFromFile` updated to accept `registeredtypes.diaschema` format (reads `modules` + `processing_units` keys — same keys, backwards compatible)
- Old `types.json` path removed once schema generation is wired
- `TypeDiscoveryService` loaded from schema path derived from `ProjectContext.diagamePath`

## File Format Notes

- `fields[].kind` matches existing `FieldKind` enum string values (`"primitive"`, `"string_id"`, `"math"`, etc.)
- `modules[].allowed_pus` is a string tag derived from `kAllowedPUs` affinity mask, or `"any"` if not constrained
- Schema file is UTF-8 JSON, tab-indented, committed to git alongside the `.diagame`

## Binding Decisions

| Decision | Compliance |
|---|---|
| PD-001 StringCRC for all IDs | `type_id` fields are the string form of StringCRC IDs — the schema is the serialised form. Compliant. |
| PD-006 VS project files source of truth | No new vcxproj required; `--dump-schema` is a flag on the existing game executable. Compliant. |

## Open Design Questions

1. **`--dump-schema` flag vs dedicated schema-dump binary:** Running the game binary with a special flag is simple but means the game's full startup runs. If startup has side effects (window creation, network), a dedicated headless schema-dump entry point may be needed. Mitigated for now since CluicheTest initialises cleanly.

2. **Schema file in git:** Committing a generated file creates merge conflict risk when two branches add components simultaneously. Acceptable at current team size; worth reconsidering at 3+ developers working on components simultaneously.
