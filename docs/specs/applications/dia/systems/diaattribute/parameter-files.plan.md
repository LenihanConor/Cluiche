# Plan: DiaAttribute Parameter Files (DiaAttribute Feature 8)

**Spec:** @docs/specs/applications/dia/systems/diaattribute/parameter-files.md
**Status:** Not Started

Can start now: the first phase (sidecar additions in DiaValueSchema and the `dia validate schema` CLI) needs nothing else. This plan
depends on no other plan. It touches Dia (DiaValueSchema, DiaCLI, DiaAttribute) and one CoW module (S-1 `TerrainRules`
and `WorldGenerationModule`). Later plans depend on it: the world-sim kit's `ParamCommandHelper`, the T-2 world data editor
(it reuses the new conformance fixtures), and the A4, A5 and A1 amendments (world-sim spec 6) all consume `ParameterFile` and
`ParamBinding`, so this plan must be Done before any of them starts building parameters. No plan may migrate a map-using consumer
before the biome registry exists (Resolved Design Question 3).

AD-001 (CoW, ask before Dia edits): signed off by the user on 2026-11-18 (spec "Binding Decisions", research section 0, D2). All Dia
edits listed in the spec's "Files Touched" are in scope. Anything outside that list (a new Dia header not named in the spec, an edit
to another Dia module) is not signed off: stop and ask. Tasks that might need more than sonnet say "ask before escalating"
(feedback_confirm_opus).

The spec's "Spec-6 resolutions" section supersedes contradicting text above it: a pack's `format` is the sidecar's `for` (no separate
pack format ids, no `base` + `overrides` shape); packs carry `"basedOn": <hex>`; `ParameterFile::SchemaHash()` exists; a stale pack
still applies, with one Warning; `ToJson(Diff)` writes `basedOn`.

## Implementation Patterns

### Phase A: sidecar additions (DiaValueSchema, `Dia/DiaValueSchema/`; Tasks 2 to 7)
- `ValueInfo.h` (namespace `Dia::ValueSchema`) gains, using `ValueList<>` (the existing Dia-container wrapper in that header, not STL):
  - `struct BandInfo { String64 mName; double mLo; double mHi; }` and `ValueList<BandInfo> mBands` on `ValueInfo`.
  - `struct MapDefault { String128 mMapKey; double mNumber; String128 mString; }` and `ValueList<MapDefault> mMapDefaults` plus
    `bool mHasMapDefault`. (A `map` entry's `default` is an object; today `mHasDefault`/`mDefaultNumber` hold scalars.)
  - `enum class ConstraintOp : uint8_t { Lt, Le, Gt, Ge, Eq, Ne }` and `struct Constraint { String128 mA; ConstraintOp mOp; String128 mB; }`.
  - `LoadResult` (in `ValueSchemaLoader.h`) gains `ValueList<Constraint> mConstraints` (top-level, file order).
- `ValueSchemaLoader.cpp` rules (all failures use the existing `LoadFailure{mFile, mEntry, mReason}`, naming the entry key; no new logging channel, the existing `VSC` channel):
  - `bands`: object of `name -> [lo, hi]`, both finite numbers, `lo <= hi`, each inside `[min, max]` when those exist; only on numeric types.
  - map `default`: object keyed by map key; every value checked against `valueType`, `min`, `max`. Resolving keys against a key source is **not** the loader's job (C++ checks in `FromValueSchema`, CLI checks via `keyRef`).
  - top-level `constraints`: array of `{a, op, b}`; `op` one of `< <= > >= == !=`. The loader checks shape only; whether `a`/`b` name known numeric keys is checked after all entries are read (a map column is addressed `<key>.<mapKey>`, so the map-key part is checked later by `FromValueSchema`, the loader only checks that the head resolves to a numeric entry or a map entry with a numeric `valueType`).
  - Add `constraints` to the allowed file keys and `bands` to the allowed entry keys (the current loader rejects unknown keys, see `bad-unknown-file-key` and `bad-unknown-entry-key`).
- Shared conformance fixtures go in `Dia/DiaValueSchema/Testing/Conformance/` (data files, not in a vcxproj; every file needs an `expected.json` entry and vice versa): `bad-band-outside-range`, `bad-band-lo-gt-hi`, `bad-map-default-wrong-type`, `bad-map-default-out-of-range`, `bad-constraint-op`, `bad-constraint-unknown-key`, `bad-constraint-non-numeric`, `good-bands`, `good-map-default-object`, `good-constraints`. Findings that need a data file (unresolved map key, violated constraint) go under `Conformance/data/` with their own expected entries, following how `good-parameter-file.schema.json` and `data/` are used today (Task 0 records the exact convention).
- CLI (`Dia/DiaCLI/dia_cli/commands/validate/`): `schema_rules.py` gains `schema.bad-band` and `schema.bad-constraint` (the same checks as the loader, mirrored; update `ENTRY_KEYS` with `bands`, `FILE_KEYS` with `constraints`). `data_rules.py` gains `data.constraint-violated` (names both keys), `data.unresolved-map-key` for object map defaults (rule id already named in AC 2), and scopes `data.default-mismatch` off `kind: parameter` entries (base parameter files no longer exist). Tests go in the existing `Dia/DiaCLI/tests/test_validate_schema_rules.py`, `test_validate_schema_data.py`, `test_validate_schema_parity.py` (extend; do not create near-duplicates).
- Parity: the existing C++ `TestValueSchemaConformance.cpp` and Python `test_validate_schema_parity.py` both read `expected.json`; the new fixtures make them agree on every case. A C++ and CLI finding mismatch on any fixture is a failure.

### Phase B: `AttributeSchema::FromValueSchema` (`Dia/DiaAttribute/`; Tasks 8 to 13)
- New `IMapKeySource.h`, namespace `Dia::Attribute`: `struct MapKeys { const Dia::Core::StringCRC* ids; const char* const* names; uint32_t count; }` and `class IMapKeySource { virtual bool GetKeys(const char* keyRef, MapKeys& out) const = 0; }` (resolves by `keyRef` string, per spec; null source allowed when there is no map entry).
- `SchemaError { String128 key; String256 reason; }` declared in `AttributeSchema.h` (and `ParamError`, `ParamWarning`, `ParamWarnings` in `ParameterFile.h`), exactly as in the spec. No `std::` type in any public signature (PD-004).
- `AttributeDefinition` gains: `AttributeKind kind` (`enum class AttributeKind : uint8_t { Float, Int, Bool, Enum }`), enum id strings kept for `ToJson` (a `DynamicArray<String64>` or equivalent Dia container, not STL), `String128 fullKey` (diagnostics and `ToJson`). The existing `HashTable<StringCRC, BandRange> bands` stays; bands now come from `ValueInfo::mBands`.
- `AttributeSchema` gains `static bool FromValueSchema(const Dia::ValueSchema::LoadResult&, const IMapKeySource*, AttributeSchema& out, SchemaError& err)` (the spec writes it with `static bool AttributeSchema::`, which is not valid C++ inside a namespace block; it is the static member), plus `Constraint` storage resolved to attribute indices (`struct ConstraintIdx { uint32_t a; ConstraintOp op; uint32_t b; }`) and `bool CheckConstraints(const float* baseValues, uint32_t count, SchemaError& err) const` (names both keys). `FromValueSchema` uses `CheckConstraints` on the defaults.
- Schema order = sidecar file order, map keys in key-source order. `GetBandSchemaVersion()` now returns the sidecar `version`.
- `FromValueSchema` failure list and naming: the spec's six failure cases, each naming the key. Entries of kinds other than `parameter` are ignored (AC 5). A map entry with no key source fails naming the key.
- Deleted in Task 13 (not before the migrations are green): `LoadFromJson`, `LoadFromJsonValue`, `ParseAttributes`, `ParseBands`, `ValidateBandRange` (private helpers).
- `Dia/DiaAttribute/Testing/AttributeTestHelpers.h` (PD-009 test utilities live beside the module) gains sidecar builders: `MakeSidecarText(...)` fixtures, a `FixtureMapKeySource`, and a `LoadSchemaOrDie(const char* text)` helper so migrated tests stay short. The module vcxproj needs a project reference to DiaValueSchema (check `DiaAttribute.vcxproj`); `dia check deps` verifies the declaration against the module doc.
- Test files: `Cluiche/Tests/GoogleTests/DiaAttribute/TestDiaAttributeSchemaFromValueSchema.cpp` (new; suite `DiaAttributeSchemaFromValueSchema*`).

### Phase C: `AttributeSet` internals (Tasks 14, 22)
- Slot storage moves from `HashTable<StringCRC, AttributeSlot> mSlots` to a schema-ordered `Dia::Core::Containers::DynamicArray<AttributeSlot>` plus a `HashTable<StringCRC, uint32_t>` name to index map (Resolved Design Question 2). The spec says `DynamicArrayC`, but the capacity is the schema's runtime size, so Task 0 confirms the right container (likely `DynamicArray`; `AttributeSet.cpp` line ~85 already calls `SetSize(count, count)`). Public behaviour unchanged: `GetValueByIndex` and `GetAttributeNameByIndex` become O(1) (today `GetAttributeNameByIndex` is O(index)).
- New O(1) accessors needed by `ParamBinding::Snapshot`: `float GetBaseValueByIndex(uint32_t)` and `void SetBaseValueByIndex(uint32_t, float)` (silent: no observers), plus a bulk path used by atomic commit (`bool ReplaceBaseValues(const float* values, uint32_t count)` which fires `OnAttributeChanged` only for changed values, after the commit). Names are placeholders: record the final names in Task 0 notes.
- Kind-aware modifiers (Task 22): `AddModifier` checks the definition's `AttributeKind`: Add and Multiply only on Float and Int; an Int result is rounded half away from zero (`std::round` semantics) then clamped; Override valid on all kinds with the value validated for the kind (bool exactly 0 or 1; enum an in-range ordinal; int a whole number). An illegal call returns an invalid `ModifierHandle` and logs `DIA_LOG_WARNING` naming the attribute (existing DiaAttribute logging channel; Task 0 records it).
- `Cluiche/Tests/GoogleTests/DiaAttribute/TestDiaAttributeModifierKinds.cpp` (new; suite `DiaAttributeModifierKinds*`).

### Phase D: `ParameterFile` (Tasks 15 to 21)
- `Dia/DiaAttribute/ParameterFile.h/.cpp`, namespace `Dia::Attribute`: `LoadPolicy`, `JsonShape`, `ParamError`, `ParamWarning`, `ParamWarnings` (`DynamicArrayC<ParamWarning, 64>` plus `dropped`), `class ParameterFile` exactly per the spec, plus `uint64_t SchemaHash() const`. `ParameterFile` is not copyable or movable (owns an `AttributeSet`).
- One private core: `bool Merge(const Json::Value& obj, LoadPolicy, float* candidate, ParamWarnings*, ParamError&)` fills a candidate `float[]` copied from the base values, validates, runs `CheckConstraints` on the candidate, and only then commits through the bulk path. Strict (`Load` defaults path, `Set`) and lenient (`ApplyPack`) differ only in the policy argument. This is how "atomic" is guaranteed; tests compare base values with `memcmp` before and after a rejected call.
- Lenient rules (AC 9): wrong `format` or `version` rejects the pack; unknown key, non-whole int, unknown enum id are dropped with a warning; out-of-range clamps with a warning; constraints run on the post-merge candidate and reject the whole pack on failure. A bool accepts JSON `true`/`false` and 0/1. Warnings past 64 increment `dropped`.
- Stale packs: `ApplyPack` compares `pack["basedOn"]` (hex string) with `SchemaHash()`; a mismatch adds exactly one warning (key `basedOn`) and the pack still applies. A pack with no `basedOn` is treated as the spec's silent default only if Task 0 / Open item 2 says so; until decided, treat a missing `basedOn` as no warning and no rejection.
- `SchemaHash()`: FNV-1a 64 over the sidecar's parameter entries in schema order (key string, kind, min, max, default, as bytes with `-0.0` normalised), independent of descriptions, labels and bands text. Exact byte layout is documented in a comment in `ParameterFile.cpp`; a test pins one known value for a small fixture.
- `Hash()`: FNV-1a 64 over base values in schema order as IEEE-754 bit patterns, `-0.0` normalised to `+0.0`; modifiers excluded.
- `Reload(sidecarText, packs, packCount, warn, err)`: builds a complete new `ParameterFile` state into a local, applies packs in order, swaps on success; on failure nothing changes. Modifiers on the existing `AttributeSet` are kept (they re-attach; Task 0 / Task 20 decide the mechanism and note it, because `AttributeSet` is not movable and holds a `HandlePool`: prefer re-initialising the schema and base values in place with `InitializeFromSchema`-style code that preserves modifier slots; "ask before escalating" if it needs `AttributeSet` redesign).
- `ToJson(Full)`: every parameter in schema order, enum ids as strings, maps nested. `ToJson(Diff)`: `format`, `version`, `basedOn`, then only values differing from their defaults. Empty diff is a valid pack (envelope only).
- Errors: `ParamError.key` names the key (`otherKey` for the second key of a constraint). Logging: `ParameterFile` itself logs nothing on failure (callers log and set module health); it logs one `DIA_LOG_WARNING` per modifier-illegal call only (Phase C). The spec's failure rule (health Error, no generation) is the consumer's (Task 26).
- Test files: `TestDiaAttributeParameterFile.cpp` (suites `DiaAttributeParameterFile*`; strict load, packs, Set, Reload, ToJson, Hash, SchemaHash, Save), `TestDiaAttributeParamBinding.cpp` (suite `DiaAttributeParamBinding*`). Fixtures use `AttributeTestHelpers.h` sidecars.

### Phase E: `ParamBinding<T>` (`Dia/DiaAttribute/ParamBinding.h`, header-only; Task 23)
- Template per spec. Storage: a fixed-capacity `DynamicArrayC<Entry, kMaxBindings>` (constant chosen in Task 24 and asserted; TerrainRules needs the largest count today, so size it from `TERRAIN_RULES_TABLE` row count rounded up) where `Entry { StringCRC key; Kind kind; ptrdiff offset; uint32_t index; }`. Member pointers are stored as byte offsets via `offsetof`-style arithmetic captured at `Bind` time, so `Snapshot` has no virtual call and no allocation.
- `BindingReport { DynamicArrayC<String128, N> unboundParameters; DynamicArrayC<String128, N> bindingsWithoutEntry; }`.
- `Snapshot(const AttributeSet&, T&)` reads `GetValueByIndex` (resolved values, modifiers included). No allocation and no hash lookup: the test uses a counting global `operator new` hook scoped to the test plus a call to the by-index path only (AC 14). `BindEnum<E>` stores the ordinal.
- Test file: `TestDiaAttributeParamBinding.cpp`.

### Phase F: S-1 migration (CoW; Tasks 24 to 26)
- `Cluiche/CoW/Shared/WorldGeneration/TerrainRules.h/.cpp`: the `TERRAIN_RULES_TABLE(X)` X-macro, `TERRAIN_RULE_ENUM/ACCESSOR/ROW` and the hand loader go; `TerrainRules` becomes a plain struct of members (same names as the current accessors so call sites change minimally) filled by `ParamBinding<TerrainRules>::Snapshot`. The static `Rule::k...` enum and `GetInt`/`GetFloat` accessors are used all over S-1 (for example `rules.GetInt(Rule::kRiverPenalty)` in `BiomeClimate.cpp`); Task 0 counts the call sites. If a thin `Get*` shim over the struct keeps the diff small, use it; record the choice in the notes. A full call-site rewrite is allowed but must be mechanical and golden-checked.
- `Cluiche/Assets/CoW/Global/WorldGen/Rules/terrain_rules.schema.json` (new, `kind: parameter` entries): one entry per table row with kind, min, max, default, description, copied from the table (no value is invented; the table is the source). Delete `terrain_rules.json` only after the goldens pass on the sidecar. `assets.catalogue.json` alias updated (Task 0 reads the current alias and records its name).
- `WorldGenerationModule.cpp` and `WorldGenSession.cpp` load the sidecar through the catalogue alias (via `ParameterFile::Load`) and keep a `ParameterFile` in the session. A load failure sets module health to Error naming the key (existing `IHealthReporter` in the module; Task 0 confirms) and generation refuses to run (AC 19).
- Tests: existing S-1 tests stay unchanged; `Cluiche/Tests/GoogleTests/CoW/TestTerrainRulesSidecar.cpp` (new; suite `TerrainRulesSidecar*`) covers: sidecar loads and equals the old table's defaults (copied as literals, so the test cannot pass vacuously), `ParamBinding<TerrainRules>::Resolve` reports both lists empty (AC 15), a deliberately broken sidecar text puts the module in health Error naming the key (AC 19). Goldens: `Tests/GoogleTests/CoW/TestWorldGenLayerGoldens.cpp` against `Golden/worldgen_layers.golden.json` (never regenerate the golden to make a test pass; stop and report).

### Verification cadence
- Per task: narrow filter with `--shards 2` (always), for example `dia run googletest --filter="DiaAttributeParameterFile*" --shards 2`. CLI tasks run the matching `pytest` files only.
- Feature-wide scoped run only in the verification task: `--filter="*DiaAttribute*:*ValueSchema*:*TerrainRules*:*WorldGen*"` with `--shards 2`, plus CLI `pytest` for `validate`. No full-suite run here (one full run happens at stack close-out). No sanitizer. No mutation checks. Perf is a Debug ballpark only.

## Open items

1. **Resolved 2026-11-18:** built in this feature as Task 7a (AC 22-25); used by `cow.<sys>.params {action: save_defaults}` and T-2. **In-place writer for sidecar defaults (Resolved Design Question 1).** The spec resolves it (a shared DiaValueSchema helper that replaces only `default` values, with a byte-identical round-trip test) but gives it no acceptance criterion, no Files Touched row and no consumer in this feature ("decide before the first consumer adds save as defaults"). This plan does not build it. Decide whether it belongs to this feature (add a task and a Files Touched row) or to the first "save as defaults" consumer (A1 `tuning.save` or T-2).
2. **Resolved 2026-11-18:** a missing `basedOn` is stale: one Warning, then applies leniently (AC 28, Task 17a). **Pack without `basedOn`.** Spec-6 resolution 2 defines the stale rule only for a pack that carries `basedOn`. Nothing says whether a pack with no `basedOn` is accepted silently, warned or rejected (hand-authored packs will often lack it). Task 17 implements "accept, no warning" as the minimal reading and flags it.
3. **Resolved 2026-11-18:** hash keys, kinds, min/max, default, enum values, bands, constraints, map `keyRef`/`keyEnum`; exclude presentation fields (AC 26-27, Task 17a). **`SchemaHash()` input.** The spec says "the schema hash of the sidecar's parameter entries (keys, kinds, ranges and defaults)". Whether bands, constraints and enum value lists are included is unstated. The plan hashes keys, kinds, ranges and defaults only, per the quoted text; confirm that bands, constraints and enum values should not stale a pack.
4. **Container for schema-ordered slots.** The spec says `DynamicArrayC` (fixed compile-time capacity) but the slot count is the schema's runtime size; Task 0 and Task 14 expect `DynamicArray`. Confirm.
5. **Unlisted users of the old loader.** `Tests/GoogleTests/DiaAttributeVisualDebugger/TestAttributeVisualDebugger.cpp` also calls `LoadFromJsonValue`, and `F2DragonStub.cpp` has no "schema asset" (inline JSON). Handled in Task 12; the spec's Files Touched table is incomplete.
6. **`ParameterFile::Reload` and modifiers.** "Modifiers are kept" through a reload needs `AttributeSet` to survive a schema re-initialisation although it is non-copyable, non-movable and owns a `HandlePool`. The mechanism is not specified. Task 18 is flagged "ask before escalating" if it needs more than in-place re-initialisation.
7. **Spec signature typo.** `static bool AttributeSchema::FromValueSchema(...)` inside a `namespace` block is not valid C++; the plan declares it as a static member of `AttributeSchema`.
8. **Map-keyed consumers.** No S-1 map is migrated here (none exists in `TerrainRules` as far as the table shows; Task 0 (h) confirms). Map support is tested only with fixtures, per Resolved Design Question 3.
