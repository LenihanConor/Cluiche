## Implementation Patterns

### Phase A: compatibility, cap, name (Tasks 2 to 4)
- `Dia/DiaBlackboard/Blackboard.h/.inl/.cpp`, namespace `Dia::Blackboard`. Constructor becomes `explicit Blackboard(uint32_t maxSlots = 32, Dia::Core::StringCRC name = {});` (the existing default constructor `Blackboard()` is covered by the defaults; `explicit` on a defaulted-args ctor: Task 0 checks nothing relies on copy-list-init `= {}`).
- Storage: `DynamicArrayC<SlotEntry*, kMaxSlots>` becomes `Dia::Core::Containers::DynamicArray<SlotEntry*>` reserved to `maxSlots` in the ctor, plus `uint32_t mMaxSlots`. Exceeding the cap still asserts (`DIA_ASSERT`, same message style as the existing check; Task 0 records it). `kMaxObservers` stays 8 (the spec does not change it).
- New members: `StringCRC mName`, `const Blackboard* mParent = nullptr`, `mutable uint32_t mChildCount = 0`. `GetName()` and `GetParent()` are const accessors.
- Compatibility: `Register`, `Unregister`, `Get`, `TryGet`, `Has`, `AddObserver`, `RemoveObserver`, `VisitSlots`, `VisitObservers` unchanged and local-only. Whether `Blackboard` is copied or held by value elsewhere (`BlackboardComponent`, `BlackboardRegistry`, `GlobalBlackboard`) is confirmed in Task 0; a `DynamicArray` member changes copy semantics, so if any holder copies a board, record it and fix the holder, not the spec.
- Test files (new, `Cluiche/Tests/GoogleTests/DiaBlackboard/`): `TestBlackboardScopes.cpp` (suites `BlackboardScopes*`: cap, name, chain, `SetParent`), `TestBlackboardNotifications.cpp` (suite `BlackboardNotifications*`: `Set`, `OnSlotChanged`). The existing `TestBlackboard.cpp` is not edited.

### Phase B: chain (Tasks 5, 6)
- `bool SetParent(const Blackboard* parent)`: refuses `this == parent`, a cycle (walk up from `parent`, fail if `this` is met), and a chain depth over 8 (depth counted from `this` up through the whole chain of `parent` plus the depth of `this`'s existing descendants is **not** tracked, so the rule applied is "the length of the chain from `this` upward after the change is at most 8"; Task 0 / Task 6 pin the exact count and note it, see Open item 1). On refusal the board is unchanged (no counter changes). A successful change decrements the old parent's `mChildCount` and increments the new one's; `SetParent(nullptr)` detaches.
- Destructor: detaches from its parent (decrement) and `DIA_ASSERT`s in Debug if `mChildCount != 0` (a parent outliving its children is the caller's duty). The assert is tested with the project's assert-testing convention (Task 0 finds how existing tests check `DIA_ASSERT`, for example a test assert handler; record it).
- `template<typename T> const T* Lookup(StringCRC key) const`: local slot, then up the chain; type-checked with the same typeTag mechanism as `Get`, mismatch asserts. `bool HasInChain(StringCRC) const` and `const Blackboard* FindOwner(StringCRC) const` walk the same way. A local key shadows a parent key.
- Chain methods are the only new read path; `Get`, `TryGet`, `Has` stay local-only (AC 1).

### Phase C: `Set` and notifications (Task 7)
- `IBlackboardObserver.h`: add `virtual void OnSlotChanged(Dia::Core::StringCRC /*key*/) {}` (defaulted, non-pure) so existing observers compile and behave as before.
- `template<typename T> void Set(StringCRC key, const T& value)`: finds the local slot (assert if not registered locally, even if a parent holds it; type mismatch asserts like `Get`), assigns, then calls `NotifyChanged(key)` which calls `OnSlotChanged(key)` once on each observer of this board only (not parents' or children's observers). A write through the mutable `Get`/`TryGet` reference does not notify; document this in the header comment on `Get`/`TryGet`.
- `Dia/DiaBlackboard/Testing/BlackboardTestHelpers.h`: the mock observer counts `OnSlotChanged` calls and records the last key (PD-009).

### Phase D: inspector (Task 8)
- `Cluiche/CluicheGameBaseline/Modules/InspectorSources/BlackboardInspectorSource.cpp` (and `.h` if the payload type needs a field): per board entry the JSON keeps the existing fields (`id`, `label`, `slots`, observers) and adds `name` (the board's `GetName().AsChar()`), `parent` (name or id of the parent, empty when none), and an `inherited` array: for each ancestor in order, `{ "from": <ancestor name>, "slots": [ {key, type, value, "shadowed": bool} ] }`. A key is `shadowed` when a nearer board in the chain holds the same key. Existing hash combine (`HashCombine` of id, slot count, observer count) is extended to include the parent link and inherited slot counts so a chain change is detected (`kChangeDetected` source).
- The existing contract fixtures (`Cluiche/Tests/GoogleTests/CluicheGameBaseline/TestBlackboardInspectorSource.cpp` and any JSON contract fixtures it uses; Task 0 lists them) must pass unchanged; add a new chain fixture and a test. Whether existing fixtures use strict key comparison (so that an added `name`/`parent`/`inherited` key breaks them) is a Task 0 finding: the spec says they pass unchanged, so additions must be backward compatible with whatever the fixture check does (Open item 2).
- Registry: `BlackboardRegistry` entries reference boards by pointer (`entry.board`); this plan does not change the registry unless Task 0 finds it needs the parent resolved by name (record it).

### Phase E: docs (Task 9)
- `Dia/DiaBlackboard/Docs/*.module.md`: responsibilities (scopes, `Lookup`, `Set`, `OnSlotChanged`, name, cap) and non-responsibilities (thread safety, propagating parent changes to child observers, `GlobalBlackboard` removal). Run `dia docs registry`.
- `docs/specs/applications/dia/systems/diablackboard/diablackboard.md`: fill in the stub system spec body (purpose, responsibilities, features table with this feature), per the spec's Files Touched row. This is the only spec file edited by this plan and only the body of the system spec; the feature spec is not edited. The rule "a system spec cannot be Done until all child feature specs are Approved" is respected by leaving the system status as it is.

## Open items

1. **Depth 8 definition.** The spec says `SetParent` refuses a chain "deeper than 8" without saying whether depth counts boards or parent links, or whether a child that already has descendants counts them. The plan pins "chain length from this board upward is at most 8 boards after the change" and tests that boundary; confirm, and note that descendants' depth is not tracked (a deep subtree re-parented under a deep board is not refused).
2. **Inspector payload compatibility.** The spec requires the existing contract fixtures to pass unchanged while the inspector gains `name`, `parent` and `inherited` fields. Whether the fixtures tolerate extra keys is unknown until Task 0 (e); if they compare the payload strictly, the spec's two requirements conflict and the user must choose.
3. **`Lookup` const parent.** `SetParent` takes `const Blackboard*`, so `Lookup`, `HasInChain` and `FindOwner` return const results only; a caller needing to `Set` on an ancestor holds that board directly. No spec gap, noted so the CoW amendment does not expect mutable chain access.
4. **Condition bridge.** Spec Open Design Question 1 (chain-aware DiaCondition accessor) stays open and is out of scope: no task changes the bridge; Task 0 (f) only confirms it still uses local reads.
5. **`GlobalBlackboard`.** It is a singleton kept as debt; its `Blackboard` member now takes the default cap of 32 through the default arguments. Task 0 (a) confirms its construction still compiles; no behaviour change is planned.
6. **Parent lifetime across PUs.** The child counter is a plain `mutable uint32_t`: correct only because boards are SimPU-only (spec Non-Goals). No task adds thread safety.
