# Feature Spec: Flush Adapters

## Parent System
@docs/specs/applications/dia/systems/diamessagebus/diamessagebus.md

## Problem Statement

Physics collision events and input events originate outside the bus — in an `EventStream` owned by `DiaRigidBody2D` and in `DiaInput`'s legacy `EventDispatcher` path respectively. Without a bridge, these events cannot participate in the bus's single-source-of-truth routing table, cannot appear in the last-tick ledger, and cannot be delivered to subscribers in the same tick they occur. The `IFlushAdapter` interface (declared in core-bus) is the seam; this feature delivers the two concrete adapters that cross it — `PhysicsBusAdapter` and `InputBusAdapter` — so every gameplay-relevant event source feeds the same bus and the same ledger, with zero same-tick latency.

## Design

### IFlushAdapter (from core-bus — not re-declared here)

The interface is declared in core-bus and lives in `Dia/DiaMessageBus/`. Adapters implement it and register themselves with the bus. The bus calls `Flush(bus)` on each registered adapter in registration order during the pre-Primary step of each `MessageBusModule::Update()`, before the Primary pass begins.

```cpp
// Declared in DiaMessageBus — reproduced here for reference.
namespace Dia::MessageBus {

    class IFlushAdapter {
    public:
        virtual ~IFlushAdapter() = default;
        virtual void Flush(Bus& bus) = 0;  // drain internal events into bus via Post<T>
    };

}
```

### PhysicsBusAdapter (lives in DiaRigidBody2D)

`PhysicsBusAdapter` holds a reference to the physics collision `EventStream`. During `Flush`, it consumes pending events and posts each one as a `CollisionEvent` addressed to `bodyA`'s entity handle via the `EntityRouter`. The `CollisionEvent` struct is authored in a `.diagamemessages` file under `DiaRigidBody2D` and generated by `dia codegen messages` — the adapter `#include`s the generated header.

```cpp
// Lives in DiaRigidBody2D — reads physics EventStream, posts to bus.
class PhysicsBusAdapter : public Dia::MessageBus::IFlushAdapter {
public:
    void Flush(Dia::MessageBus::Bus& bus) override {
        // drain physics EventStream into bus
        mCollisionStream.Consume(mReaderIdx, mScratch);
        for (auto& ev : mScratch) {
            bus.Post<CollisionEvent>(
                { Bus::kEntityRouterId, ev.bodyA.bits() },
                { ev.bodyB, ev.impulse, ev.normal });
        }
    }
};
```

The physics module retains ownership. It registers `this` with the bus via `Bus::RegisterFlushAdapter(&mPhysicsBusAdapter)` in `OnStart` and the bus holds a non-owning pointer.

### InputBusAdapter (lives in DiaInput)

`InputBusAdapter` replaces the `EventDispatcher` path in `DiaInput::InputSourceManager` (see Feature: eventdispatcher-removal, which must complete first). During `Flush`, it drains pending input events from `DiaInput`'s internal source and broadcasts each one. Input message types (`KeyDownEvent`, `MouseButtonEvent`, etc.) are authored in a `.diagamemessages` file under `DiaInput` and generated via `dia codegen messages`. Adapters post via `bus.Broadcast<T>` (equivalent to `bus.Post<T>({ Bus::kBroadcastRouterId, 0 }, msg)`) because input events are system-wide.

```cpp
// Lives in DiaInput — drains input events, broadcasts to bus.
class InputBusAdapter : public Dia::MessageBus::IFlushAdapter {
public:
    void Flush(Dia::MessageBus::Bus& bus) override {
        mInputSource.ConsumeEvents(mScratch);
        for (auto& ev : mScratch) {
            // Dispatch on event kind — generated types per .diagamemessages
            ev.Visit([&bus](const KeyDownEvent& e)        { bus.Broadcast(e); },
                     [&bus](const KeyUpEvent& e)          { bus.Broadcast(e); },
                     [&bus](const MouseButtonEvent& e)    { bus.Broadcast(e); },
                     [&bus](const MouseMovedEvent& e)     { bus.Broadcast(e); });
        }
    }
};
```

The input module retains ownership and registers `this` with the bus via `Bus::RegisterFlushAdapter(&mInputBusAdapter)` in `OnStart`.

### Timing guarantee

Because both adapters run in the pre-Primary step — before the Primary pass drains type queues — every message they post is available to Primary-pass handlers in the **same tick**. This is not a contract of the adapter interface; it is a contract of the bus's two-pass flush order (SD-MBX2-002). Adapters posted during the Reaction pass would violate this guarantee; neither adapter registers for that pass.

### Message type authorship

Concrete message types are **not** hand-authored in adapter source. They are declared in `.diagamemessages` IDL files living alongside the module that owns them:

- `Dia/DiaRigidBody2D/Messages/physics_messages.diagamemessages` → generates `physics_messages.h`
- `Dia/DiaInput/Messages/input_messages.diagamemessages` → generates `input_messages.h`

Adapters `#include` the generated headers. The `dia validate manifest` and `dia docs precommit` staleness checks apply to both files (see Feature: diagamemessages-format).

### Module placement rule

Adapters that wrap engine subsystems live in **those engine modules**, not in `DiaMessageBus`. `PhysicsBusAdapter` is a source file in `DiaRigidBody2D`; `InputBusAdapter` is a source file in `DiaInput`. Both modules add `DiaMessageBus` to their `vcxproj` references. `DiaMessageBus` itself has no knowledge of either adapter — it only exposes the `IFlushAdapter` interface and `RegisterFlushAdapter`.

### Prerequisites and coordination

- **Prereq: core-bus** — `IFlushAdapter`, `Bus::RegisterFlushAdapter`, `Bus::Post`, and `Bus::Broadcast` must exist before either adapter can compile.
- **Prereq: eventdispatcher-removal** — that feature runs first and deletes `InputSourceManager::UpdateModern` + `LegacyEventConverter`, leaving the legacy `Update(EventData&)` path intact so input keeps working in the interim (no dead gap — confirmed: `InputSourceManager` retains `Update(EventData&)` independent of any `EventDispatcher`/bus path). `InputBusAdapter` is then built into the vacated slot. Order: **eventdispatcher-removal first, flush-adapters second** — matching the system plan (task 9 prereq 8) and eventdispatcher-removal's own ordering note.
