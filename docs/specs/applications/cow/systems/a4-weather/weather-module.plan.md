# Plan: A4 WeatherModule & Deferred Step (A4 Weather Feature 3)

**Spec:** @docs/specs/applications/cow/systems/a4-weather/weather-module.md
**Status:** Not Started
**System plan:** @docs/specs/applications/cow/systems/a4-weather/a4-weather.plan.md (row 3)

**Start conditions.** Needs A4 Features 1, 2 and 6 built (`WeatherSimulation`, `WeatherRunner`, parameters, `ApplyPreset`), World Step Features 1 and 2 (`IWorldStepStage`, `WorldStepModule::RegisterStage`) and DiaDeferredStep Features 1 to 4 (`IParallelExecutor`, the capped executor, `DeferredStepModule`). S-1 `WorldGenerationModule` is already built. **Startable earlier with fakes:** tasks 2 to 10 are pure or driver-level (fake `WorldStepModule`, fake `WorldGenerationModule` event source, fake message bus, `SerialExecutor`, synchronous launcher) and need only A4 Features 1, 2 and 6 plus the `IWorldStepStage` header from World Step Feature 1. Tasks 11 to 18 need the real `WorldStepModule` and `DeferredStepModule`. Task 12 (real capped executor, 2 workers) needs DiaDeferredStep Feature 2.

No Dia files are added or edited (AD-001 not triggered). If any task finds it needs one, stop and mark it `AD-001 ask first`.

## Implementation Patterns

### Files and layout
- `Cluiche/CoW/Modules/WeatherModule.h/.cpp` (SimModule, `IHealthReporter`), `WeatherStage.h/.cpp` (`class WeatherStage : public IWorldStepStage`, constructed by the module, holds a back-reference to module state through a small `WeatherModuleState` struct so the stage is testable without the module), `WeatherMessages.h` (hand-written POD, follow `GameSpeedMessages.h`), `SpinUpJob.h/.cpp` (pure).
- Tests: `Tests/GoogleTests/CoW/Weather/{TestSpinUpJob,TestWeatherStage,TestWeatherModule}.cpp`. Test helpers live in `Cluiche/CoW/Shared/Weather/Testing/` (`FakeWorldStepRegistry.h`, `FakeWorldGenerationSource.h`, `SynchronousLauncher.h`, `ObservingExecutor.h`), per the "test utilities ship with libraries" rule, not in GoogleTests.
- Namespace `CoW::Weather`. Members `m` prefix, constants `k` prefix, log channel `WTH`.

### Task 3: SpinUpJob (pure)
- `class SpinUpJob { SpinUpJob(WeatherSimulation& sim, const WeatherTerrain&, uint32_t revision, uint32_t weeks, const IRevisionSource&); enum class Result { Completed, Cancelled }; Result Run(IParallelExecutor&); }`.
- `IRevisionSource { virtual uint32_t GetTargetRevision() const = 0; }` is the only thing it reads from the module. The job checks `GetTargetRevision() != mRevision` **between weeks** and returns `Cancelled`. The revision read is a `std::atomic<uint32_t>` load owned by the module (this is state private to the module and its own job, not a PU-boundary read; same reasoning as DiaDeferredStep's CapGate).
- Spin-up runs `spinup_weeks` from calendar offset 0 (Spring): the job passes `startWeekOffset` 0 to `WeatherRunner::Start` (S-2.5 Feature 3). With 52 weeks it ends at the end of Winter, one step before Spring; the first live step takes its season from its step day and may differ. Accepted, no correction (amendment 4).
- It delegates the week loop to `WeatherRunner::Start(...)` so the oracle (AC 7) is the same code. If `WeatherRunner` exposes no per-week hook, add a cancel-predicate parameter to the runner in CoW Shared; do not duplicate its loop.
- It never publishes anything. Spin-up is silent.

### Task 4 to 6: WeatherStage
- `Capture(StepKey stepDay)`: promote, drain queue, `mCaptureRevision = mActiveRevision`, `sim.Capture(Season(SeasonOf(stepDay) % 4), *baseline)`. The season/week helpers are free functions in `WeatherCalendar.h` (`WeekOf`, `SeasonOf`, `SeasonForStep`) using the real `kDaysPerSeason`, so AC 11 is a table test.
- `Commit()` returns `bool`: false for a discarded step (revision mismatch). On success: `sim.Commit()`, then `sim.SetCommittedWeek(WeekOf(capturedDay))` (Feature 2 amendment, `uint64_t`), then publish `WeatherUpdated{week, season}` through the injected `IWeatherPublisher` seam (module supplies the bus; tests supply a recorder). The captured day and season are stored at `Capture`, never recomputed at `Commit`.
- Discard path: increment `mDiscardedSteps`, one Info log, no message.
- `IsReady()` is the formula in the spec; it also checks `mUnhealthy` causes (no water source, generation failed).
- `Run(exec)` reads only `*mActive` and nothing in the module. The DFS-002 poison test: after `Capture`, overwrite the parameter copy, queue contents and terrain copy with garbage, then `Run` and compare to a clean run.

### Task 7 to 9: Mutation queue
- `MutationQueue` is a fixed-capacity `DynamicArrayC<Mutation, 128>`; `Mutation` is a tagged POD (`SetParam`, `ParamOverrides`, `Forcing`, `RegionForcing`, `BiomeChange`, `Preset`, `Reload`, **`StateReplace`**, **`ClearWindOverrides`**; amendment 1). Overrides carry a validated, merged `WeatherParameters` copy, not a `Json::Value`, so draining cannot fail halfway (AC 20 atomicity).
- Queue methods validate **before** enqueue (`SetParam` on a copy via Feature 1) and return false with `ParamError` for bad input; a full queue returns false, logs one Warning (rate-limited per drain) and sets Degraded.
- `QueueStateReplace(const WeatherStateRecord&)` stores a decoded weather-state record (applied at `Capture` like a preset: reseed then restore; the apply branch is built in `weather-save.plan.md` Task 11, this feature only defines the entry, storage and drain order). `WeatherStateRecord` is a plain struct in `WeatherStateRecord.h` (width, height, cell count, `int64_t` week, params hash, `WeatherFields`, biome array); the codec that fills it is Feature 4's. `QueueClearWindOverrides()` removes every wind override at the next `Capture`; it needs a `WeatherSimulation` call that removes all `WindOverride` forcings (add `ClearWindOverrides()` to the class here if Features 2 and 6 have not).
- `QueueRegionForcing(const WeatherForcing&, const DynamicArrayC<uint32_t>& cells)` (part of this feature's API, not a later amendment) is stored with a fixed-capacity cell list copy; this is the amendment Feature 5 consumes.
- Drain order is arrival order, all inside `Capture`, before `sim.Capture`.
- Reload re-reads the file inside `Capture`. A failed reload keeps the previous parameters and logs.

### Task 10: Baseline provider
- `SetBaselineProvider(IBiomeSeasonalBaseline*)` stores a raw non-owning pointer; null restores the table. A `ClampingBaseline` wrapper clamps to [0, 1] at the call site inside `Capture` and logs one Error per biome/season (a 13 x 4 bitset, no allocation). Provider-called-off-SimPU check (AC 17) uses a provider that records `std::this_thread::get_id()` and fails when it differs from the test thread; `Run` is executed on a worker through the real executor in task 12.

### Task 11 to 12: Ingest and spin-up
- Spin-up completion (amendment 2): the job writes its result into a SimPU-owned `SpinUpSlot` (atomic state `Idle/Running/Done/Cancelled`, the revision, and the simulation pointer). `WeatherModule::DoUpdate` polls the slot each update; on `Done` with the target revision it sets `mPending`. No bus message, no callback onto SimPU.
- Subscribe to `WorldGenerationComplete`/`WorldGenerationFailed` through the message bus; call `HoldGeneration()` in `DoStart` and `ReleaseGeneration()` once both subscriptions are in place.
- On Complete: `mTargetRevision` store first (cancels), then copy terrain from `GetCurrentWorld()` into a `WeatherTerrain` (module never keeps the pointer), EC-01 check, build a fresh `WeatherSimulation`, launch.
- `ISpinUpLauncher { virtual void Launch(std::function-free callable, JobTag) }` is the seam; both launchers publish through the `SpinUpSlot`. `SynchronousLauncher` runs inline; `JobSystemLauncher` uses `JobSystemService::TrySubmit(fn, tag)` with the `world` tag and the DeferredStep capped executor. If `TrySubmit` fails, fall back to running inline on SimPU with one Warning (never drop). Completion is written to the `SpinUpSlot` and polled in `DoUpdate` (see above); no mailbox, bus message or callback.
- Every job result carries `(revision, visitGeneration)`; both must match on arrival or the sim is destroyed and a Warning logged.

### Task 13 to 14: Config, manifest, parameters
- Season arithmetic everywhere uses the real `kDaysPerSeason` and `kDaysPerWeek` from `GameSpeedController.h`, never a literal 91 or 7 (amendment 5).
- `spinup_weeks` parsed as an integer in `[0, 520]`; a float or out-of-range value is a config error naming the key (AC 2). Reuse World Step's config-error helper if present.
- Manifest: stage-scoped instance, listed after `WorldStepModule`; `dia validate manifest` ordering rule is World Step Feature 2's (AC 3 of that spec). This feature adds the type, dependencies and soft dependencies only.
- Parameters read once in `DoStart` through `LoadWeatherParameters`; failure falls back to `DefaultWeatherParameters()` with an Error naming the dotted key and Degraded.

### Task 15: Observability
- `IHealthReporter` with a small cause bitmask: `kFallbackParams`, `kFallbackBaseline`, `kDiscardedStep`, `kQueueFull` (Degraded); `kNoWaterSource`, `kGenerationFailed` (Unhealthy). `DIA_TRACE_ZONE` on `Capture`, `Commit`, spin-up job. Only SimPU writes health and logs (SD-PERF-7).

### Task 16 to 17: Lifecycle and placeholder
- `DoStop`: `UnregisterStage`, set cancel (store a fresh `mTargetRevision` sentinel), join the job by waiting on its completion flag, destroy both sims, clear queue, release hold if held. A per-visit `mVisitGeneration` increments in `DoStart`.
- Delete `JobSystemPlaceholderConsumerModule.*`, its `cow_main.diaapp` entry and vcxproj lines (use `dia docs` for the vcxproj lines where a remove command exists, otherwise edit both `.vcxproj` and `.filters` by hand). `dia check` orphan-provider must pass with `WeatherModule` as consumer.

### Verification cadence
- Per task: `dia run googletest --filter="SpinUpJob*:WeatherStage*:WeatherModule*:WeatherSimulation*" --shards 2`. One full `dia run googletest --shards 2` in the full-verification task only. No mutation checks. Release perf gates (spin-up wall time) are reported, not enforced.
- Concurrency tests use counters and fake executors, never sleeps.
