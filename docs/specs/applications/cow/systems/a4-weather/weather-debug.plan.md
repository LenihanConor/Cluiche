# Plan: A4 Weather Debug (A4 Weather Feature 5)

**Spec:** @docs/specs/applications/cow/systems/a4-weather/weather-debug.md
**Status:** Not Started
**System plan:** @docs/specs/applications/cow/systems/a4-weather/a4-weather.plan.md (row 5)

**Start conditions.** Needs `weather-module.plan.md` done (layers and the mutation queue with `QueueRegionForcing`) and A4 Feature 6 built (`ApplyPreset`, presets, used by `load_preset`). The spec also lists Feature 4's state codec for `state export`/`import`, so task 15 additionally needs `weather-save.plan.md` tasks 3 and 4 (the pure codec). DiaCellLayers, DiaCellHistory, DiaValueSchema, `SimQueryHostModule`, `DiaDebugDomainRegistry`/`DiaDebugPanel` and DiaObservation are built. **Startable earlier with fakes:** tasks 4 to 9 are pure (command model, detectors, overlay plan, `ExplainCell`) and need only A4 Features 1 and 2 plus hand-built terrain; tasks 10 to 19 use a fake `CellLayerRegistry`, fake `SimQueryHostModule` and fake `CellHistoryRecorder`. The three spikes (tasks 1 to 3) can start now.

No Dia files are added or edited. All DiaCellLayers, DiaCellHistory, DiaValueSchema and debug-domain APIs are used as built; any task that would need a Dia change is `AD-001 ask first`.

## Implementation Patterns

### Files and layout
- `Cluiche/CoW/Modules/WeatherDebug/`: `WeatherLayerRegistration`, `WeatherWindOverlay`, `WeatherCommands`, `WeatherCellDetails`, `WeatherHistoryEvents`, `WeatherDebugDomain` (`DIA_DEBUG` only).
- Pure, `Cluiche/CoW/Shared/Weather/Debug/`: `WindOverlayPlan`, `WeatherCommand` (typed model, parser, validation, `IWeatherCommandSink`), `StormDetector`, `DroughtDetector`, `ExplainCell`.
- Schema: `Assets/CoW/Global/Weather/weather_schema.json`.
- Tests: `Tests/GoogleTests/CoW/Weather/{TestWindOverlayPlan,TestWeatherCommands,TestWeatherDetectors,TestWeatherCellDetails,TestWeatherLayers}.cpp`. Fakes in `Cluiche/CoW/Shared/Weather/Testing/`.
- Layers, commands and metrics compile in all configurations; the `IDebugDomain`, card and overlay draw callback are `#if DIA_DEBUG`.

### Tasks 1 to 3: Spikes (gate later tasks)
- **Task 1, panel stream.** Find the stream the debug panel actually reads for a domain's SimPU values (not the `debug.domain_state` mutex precedent). Output: the named stream and message type, and the shape of `WeatherDebugStats`. Gates task 20.
- **Task 2, history read.** Find the exact DiaCellHistory read call that returns per-week floats for a tracked layer (and how to ask "is `weather.precipitation` tracked" and "what window is retained"). Output: the signature, and a thin `PrecipitationHistoryAdapter : IPrecipitationHistory` stub. Gates tasks 6 and 17.
- **Task 3, GDD hotkey table.** Read the S-2.5 GDD hotkey table and record the exact key per layer (Snow = K); read `CellLayerDesc` and `CellOverlayDesc` field names. Gates task 10.

### Tasks 4 to 5: Typed command model and sinks
- `struct WeatherCommand` is a tagged union of `Force`, `WindSet`, `WindSetRegion`, `WindClear`, `ParamsReload`, `ParamsSet`, `StateExport`, `StateImport`, `LoadPreset`, `FindStorms`, `FindDroughts`, `FindRainShadow`, `InfoProfile`, `InfoMemory`. `ParseWeatherCommand(const Json::Value&, WeatherCommand&, CommandError&)` validates all ranges and names the offending field. Parse once; the handler and both sinks consume the typed value only.
- `class IWeatherCommandSink { virtual bool Apply(const WeatherCommand&, CommandReply&) = 0; }`. `QueuedSink` calls Feature 3's `Queue*` methods. `DirectSink` is bound to a `WeatherSimulation&` and applies between steps (headless). Equivalence (AC 17) is one test running the same command list and steps against both and comparing committed state byte for byte.
- Degrees on screen counter-clockwise (0 to 360) convert through one helper shared with Feature 2's wind code; do not re-derive the conversion.
- A full queue returns a clear error in the reply (AC 19), never a silent drop.
- Feature 3's queue today has no entry types for `StateReplace` (state import) or `ClearWindOverrides`. Add them to `MutationQueue` as part of tasks 5 and 15 (CoW code; spec amendment recorded in notes), within the 128 capacity.

### Tasks 6 to 9: Pure detectors, overlay plan, details
- `StormDetector`: connected components over hex neighbours of `pressure < storm_pressure`, size, anchor (lowest-pressure cell, ties by lowest index for determinism). `DroughtDetector(const IPrecipitationHistory&, weeks, dry_threshold)` returns cell sets grouped by S-1 region, or an error naming the retained window.
- `WindOverlayPlan`: input committed `windDirection`, `windSpeed`, `pressure`, grid, `WindOverlayConfig`; output `DynamicArrayC<Arrow, kMaxArrows>` with `kMaxArrows = 2700` (the config cap), `Arrow{cell, strideTier, score}`. Algorithm exactly as the spec: 4x4 aligned blocks, `variation` as speed-weighted circular spread plus speed range scaled to [0,1], storm flag, stride 1/2/4, truncation by lowest score stable by block index, base arrows always kept, `windSpeed < 0.02` omitted. Deterministic: no hash-order or float-accumulation-order dependence (accumulate in index order).
- Config validated in `ValidateWindOverlayConfig(...)`, naming the key, falling back to defaults.
- `ExplainCell(const WeatherSimulation&, cell)` calls Feature 2's exported `PrevailingDirection`, `PressureGradient`, `SnapWindDirection`; this feature only changes their linkage (export), never behaviour.

### Tasks 10 to 13: Layers, overlay, details, command registration
- Layer registration after `WorldGenerationComplete` with `CellLayerRegistry::Register(CellLayerDesc)`; base layer, pull callback `read(float*, uint32_t)` copying the committed array, `version()` = module commit counter. Count mismatch writes zeros and logs once. Labels, ramps, `min`/`max`, hotkeys from `weather/<key>` schema entries; hotkey clash logs a Warning and the later layer gets none.
- Details registered via `CellLayerRegistry::Details()` (<= 64 rows), single-selected cell only.
- Seven names registered through `SimQueryHostModule` with `SimHelpInfo` (description 1 to 256 chars, category `weather`, owner `WeatherModule`, up to 16 `ValueParam`s). `RegisterAll()` records each success and on any failure unregisters those already registered in that call, sets Degraded naming the failing name. The fake host can be told to fail the Nth registration.

### Tasks 14 to 17: Handlers
- One handler per name: parse to `WeatherCommand`, `QueuedSink::Apply`, format the reply (it says the change latches at the next `Capture` and names the week when known). `DIA_TRACE_ZONE` per handler.
- `state export` writes to `out/CoW/weather_states/<file>.json` using Feature 4's codec; the file name is validated (no path separators, no `..`). `import` fully validates (envelope, dimensions, finite values) before anything is queued. The `cow.weather_state` envelope is not defined in Feature 4 (see Open items); task 15 defines it minimally (`format`, `version`, then the codec's fields) and records it.
- `find rain_shadow`: mean precipitation over upwind and downwind neighbours within 3 steps along the cell's snapped wind axis.

### Tasks 18 to 19: Events, metrics, health
- Events emitted from `WeatherStage::Commit` via `CellHistoryRecorder::Emit(HistoryEvent{type, group, cell, payloadJson, text})` with compact payload under 1 KB. Storm: at most 4 per week, not re-fired for a storm whose anchor was in a storm last week (keep last week's anchor-in-storm bitset, a fixed array). Drought: every 4th applied week, once per region per episode (per-region reported flag cleared by a non-dry week), skipped with one Info log per world if the layer is untracked.
- Event schema entries `kind: "event"` in `weather_schema.json` for both types.
- Metrics `cow.weather.step_ms`, `cow.weather.raining_cells`, `cow.weather.mean_moisture` registered with `MetricInfo`, written once per applied step on SimPU only. `step_ms` is the sum of per-pass CPU from Feature 2's profile data.

### Task 20: Debug domain and card
- `WeatherDebugDomain : IDebugDomain`, description <= 80 chars, accent from `DebugGroupAccents`, registered with `VisualDebuggerModule::RegisterDomain`. It reads a `WeatherDebugStats` struct delivered by the stream found in task 1; it never reads module state. Card toggles the overlay and posts the same JSON commands through the console path.

### Verification cadence
- Per task: `dia run googletest --filter="WindOverlayPlan*:WeatherCommand*:WeatherDetector*:WeatherCellDetails*:WeatherLayers*" --shards 2`. One full `dia run googletest --shards 2` in the verification task. No mutation checks. No layer goldens (Feature 6 owns them). Release timing is reported, not gated.

## Open items

1. **Feature 4 dependency.** The spec lists Features 1, 2, 3, 4, 6; the planned start condition names only the module and Feature 6. Task 15 needs Feature 4's codec.
2. **State envelope.** `cow.weather_state` is referenced but Feature 4 defines no envelope (only the participant record). Task 15 defines a minimal one; confirm it.
3. **Queue entry types.** Feature 3's queue lists forcings, biome edits, parameter sets, preset and reload. `state import` (replacement) and `wind clear` need two more entry kinds. Task 6 adds them as a Feature 3 amendment.
4. **`QueueRegionForcing` is both in Feature 3's API already and listed as an amendment in this spec.** Treated as present; confirm.
5. **13 pass entries** (AC 18) is stated without a source; verify against Feature 2's pass list in task 17.
6. **Drought timing.** Events emit from `Commit` before the driver's next sample, so the history seen by `DroughtDetector` does not yet contain the week just committed.
7. **Hotkey table and panel stream** are resolved only by spikes 1 and 3; if the stream route needs a new Dia message type that is an `AD-001 ask first` item.
